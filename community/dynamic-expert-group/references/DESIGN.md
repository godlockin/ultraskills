# 动态专家组技能 - 设计文档

## 1. 设计背景与目标

### 1.1 解决的问题

在处理复杂任务时，单一视角往往存在局限性：
- 技术专家可能忽略业务价值
- 业务专家可能低估技术风险
- 缺乏系统性的讨论和决策机制

### 1.2 核心目标

1. **动态组建** - 根据任务特征自动匹配专家
2. **多维分析** - 并行获取不同领域视角
3. **共识决策** - 通过讨论和投票达成决策
4. **知识沉淀** - 动态生成的专家可复用

---

## 2. 核心理念

### 2.1 Map-Reduce 模式

借鉴大数据处理的 Map-Reduce 思想：

```
Map (并行分析): 任务 → [专家A分析, 专家B分析, 专家C分析]
Reduce (聚合决策): [分析1, 分析2, 分析3] → 决策
```

- **Map 阶段**: 每个专家独立分析，不受其他专家影响，确保观点多样性
- **Reduce 阶段**: 汇总观点、讨论分歧、投票决策

### 2.2 渐进式专家匹配

```
模糊输入 → 提问细化 → 明确任务 → 匹配专家
```

- 一句话输入：通过提问逐步细化
- 结构化输入：直接匹配专家

### 2.3 组长协调机制

解决投票僵局问题：
- 多数同意 → 通过
- 僵局（≤50%） → 组长打断，按最优方案预演
- 最多3轮讨论 → 防止无限争论

## 3. 专家模型

### 3.1 专家属性

| 类别 | 属性 | 说明 |
|------|------|------|
| 基本信息 | id, name, name_cn, domain, level, avatar | 标识和定位 |
| 性格 | personality_type, traits, communication_style | 行为特征 |
| 背景 | education, experience, background_story | 来历设定 |
| 思维 | thinking_framework | 分析框架 |
| 决策 | decision_style, risk_tolerance | 决策方式 |
| 工作 | work_style, input_format, output_format | 协作方式 |
| 场景 | best_for, avoid, trigger_keywords | 适用场景 |

### 3.2 级别体系

| 级别 | 标签 | 适用场景 |
|------|------|----------|
| master | 战略级 | 企业战略、长期规划 |
| principal | 架构级 | 系统设计、技术选型 |
| senior | 执行级 | 代码实现、运营执行 |
| expert | 专项级 | 安全审计、危机处理 |

### 3.3 领域覆盖

```
tech/          → 技术开发
business/      → 商业决策
humanities/    → 人文社科
media/         → 传播传媒
management/    → 组织管理
```

## 4. 工作流设计

### 4.1 完整流程

```
┌─────────────────────────────────────────────────────────────┐
│ 1. 任务输入                                                  │
│    - 模糊输入: 一句话描述                                    │
│    - 清晰输入: 结构化描述                                    │
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. 任务分析 (默认分析师)                                     │
│    - 识别任务类型                                            │
│    - 评估复杂度 (L1-L4)                                      │
│    - 确定涉及领域                                            │
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. 搜索专家                                                  │
│    - 关键词匹配                                              │
│    - 任务模式映射                                            │
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ 4. 组建专家组                                                │
│    - 必须: 默认分析师 + 领域专家                             │
│    - 可选: 项目管理、战略顾问、教练                          │
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ 5. 并行分析 (Map)                                            │
│    - 各专家独立分析                                          │
│    - 输出结构化分析报告                                      │
│    - 使用 Task tool 并行执行                                  │
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ 6. 讨论投票 (Reduce)                                         │
│    - 汇总观点                                                │
│    - 讨论分歧                                                │
│    - 投票决策                                                │
└────────────────────────────┬────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────┐
│ 7. 执行交付                                                  │
│    - 按决策执行                                              │
│    - 产出交付物                                              │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 复杂度与专家组配置

| 复杂度 | 特征 | 专家组 |
|--------|------|--------|
| L1 | 单模块、小改动 | 分析师 + 1专家 |
| L2 | 多模块、需协调 | 分析师 + 2专家 + PM |
| L3 | 系统级、跨团队 | 分析师 + 2资深 + PM |
| L4 | 公司级、长期 | 分析师 + 2资深 + 战略 + 教练 |

## 5. 协作机制

### 5.1 独立分析原则

- 每个专家看到相同的任务背景
- 专家之间不直接交流，避免从众
- 使用 subagent 并行执行

### 5.2 投票机制

- 投票阈值: 多数同意 (>50%)
- 每个专家对方案可投: 赞成 / 反对 / 弃权
- 弃权不计入分母

### 5.3 僵局处理

```
第1轮投票 → 僵局 → 重新分析讨论
第2轮投票 → 僵局 → 组长打断，按最优方案预演
第3轮投票 → 无论结果，执行组长决策
```

### 5.4 组长职责

1. 协调讨论进程
2. 打断过长争论
3. 在僵局时做出最终决定
4. 确保决策落地

## 6. 持久化设计

### 6.1 存储位置

```
references/experts/
├── tech/              # 预设专家
├── business/
├── humanities/
├── media/
├── management/
└── generated/         # 动态生成的专家

/tmp/dynamic-expert-group/
└── <task_id>/
    ├── team.json      # 专家组配置
    ├── analyses/      # 各专家分析
    ├── discussion.md  # 讨论记录
    └── decision.md    # 最终决策
```

### 6.2 精简输出策略

不保存完整讨论过程，只保存：
- 关键分歧点
- 决策理由
- 风险提示

### 6.3 专家复用

动态生成的专家：
1. 保存到 `generated/<domain>/`
2. 格式与预设专家一致
3. 下次搜索时可被匹配
4. 随专家库索引重建自动纳入

## 7. 扩展机制

### 7.1 添加新专家

1. 按模板创建 markdown 文件
2. 放置到对应领域目录
3. 运行 `init_expert_lib.py` 重建索引

### 7.2 自定义任务模式

在 `task_patterns.md` 中添加：
- 任务类型
- 推荐专家组合
- 复杂度评估

### 7.3 调整协作规则

在 `SKILL.md` 中可修改：
- 投票阈值
- 讨论轮次上限
- 组长决策时机

## 8. 使用示例

### 示例1: 技术架构决策

**输入**: "我们要重构用户服务，改成微服务架构"

**流程**:
1. 分析: 技术重构，L3复杂度
2. 搜索: 架构、安全、运维
3. 组团: 陈架构 + 安全李 + 运维王
4. 并行分析:
   - 架构师: 微服务拆分方案
   - 安全: 安全加固方案
   - 运维: 部署和监控方案
5. 讨论: 整合方案，解决冲突
6. 投票: 通过
7. 交付: 重构方案 + 实施计划

### 示例2: 营销活动策划

**输入**: "新产品上线，要做一个传播方案"

**流程**:
1. 分析: 营销活动，L2复杂度
2. 搜索: 营销、内容、社交
3. 组团: 营销吴 + 内容孙 + 社交郑
4. 并行分析:
   - 营销: 整体策略
   - 内容: 创意方向
   - 社交: 传播渠道
5. 讨论: 整合成完整方案
6. 投票: 通过
7. 交付: 营销方案 + 执行日历

## 10. 设计原则总结

1. **独立性**: 专家分析互不影响
2. **多样性**: 多领域视角全覆盖
3. **系统性**: 结构化工作流
4. **可扩展**: 专家库可动态扩充
5. **可复用**: 动态专家可沉淀
