# Task Analyzer - 任务分析与优化器

> 当用户输入一个模糊的任务命令（如"写一个天气应用"）时，自动进行深度分析和优化，生成结构化、可执行的任务定义。

## 🎯 目标 (Goal)

* 识别用户输入是否为"任务布置类"命令
* 深度分析用户的潜在需求、思路和背景
* 挖掘可能的要求、限制和约束条件
* 明确任务目标和成功标准
* 生成优化后的、结构化的任务描述

## 🧠 触发条件 (Trigger Conditions)

当用户输入符合以下特征时，自动触发此 Skill：

1. **任务初始化命令**：如"写一个..."、"创建..."、"开发..."、"帮我做..."
2. **模糊需求描述**：缺乏具体细节的简短描述
3. **大段任务描述**：包含多个要求但结构不清晰的长文本
4. **项目启动请求**：需要规划和分解的复杂任务

**示例触发输入**：
* "写一个天气应用"
* "帮我做个博客系统"
* "创建一个类似 Notion 的笔记应用，要支持 Markdown..."
* "我想做个电商网站，要有用户登录、商品管理、购物车..."

## 🚀 分析框架 (Analysis Framework)

### Step 1: 命令类型识别

首先判断输入类型：
* ✅ **任务布置类**：需要创建、开发、设计新事物
* ❌ **问答类**：仅需回答问题
* ❌ **操作类**：执行简单命令（如"运行测试"）

### Step 2: 五维深度分析

对任务布置类命令进行五维分析：

```
┌─────────────────────────────────────────────────────────────────┐
│                      📊 任务分析报告                              │
├─────────────────────────────────────────────────────────────────┤
│ 1️⃣ 用户需求 (User Needs)                                        │
│    - 表面需求：用户明确说出的需求                                   │
│    - 潜在需求：用户可能没说但实际需要的                             │
│    - 隐含期望：基于常识推断的期望                                   │
├─────────────────────────────────────────────────────────────────┤
│ 2️⃣ 用户思路 (User Approach)                                      │
│    - 用户可能的技术偏好                                            │
│    - 期望的实现方式                                                │
│    - 风格倾向（简约/功能丰富/创新性）                               │
├─────────────────────────────────────────────────────────────────┤
│ 3️⃣ 背景上下文 (Context)                                          │
│    - 项目类型（个人/商业/学习）                                     │
│    - 技术栈环境（如有）                                            │
│    - 目标用户群体                                                  │
│    - 使用场景                                                      │
├─────────────────────────────────────────────────────────────────┤
│ 4️⃣ 约束与限制 (Constraints)                                       │
│    - 技术约束：必须/不能使用的技术                                  │
│    - 时间约束：是否有紧迫性                                        │
│    - 资源约束：复杂度限制                                          │
│    - 兼容性：需要支持的平台/浏览器                                  │
├─────────────────────────────────────────────────────────────────┤
│ 5️⃣ 目标与验收 (Goals & Acceptance)                                │
│    - 核心目标：必须实现的功能                                       │
│    - 扩展目标：可选的增强功能                                       │
│    - 成功标准：如何判断任务完成                                     │
│    - 交付物：最终产出是什么                                        │
└─────────────────────────────────────────────────────────────────┘
```

### Step 3: 澄清问题生成

基于分析，生成需要向用户确认的关键问题：

```markdown
## ❓ 需要您确认的问题

1. **技术栈选择**：您倾向于使用什么技术？（如 React/Vue/原生）
2. **功能范围**：以下功能是否需要？
   - [ ] 功能 A
   - [ ] 功能 B
3. **约束确认**：是否有以下限制？
   - 必须离线使用？
   - 需要支持移动端？
4. **优先级排序**：以下哪个最重要？
   - 开发速度
   - 代码质量
   - 功能完整性
```

### Step 4: 优化后的任务描述

输出结构化的、优化后的任务描述：

```markdown
## 📋 优化后的任务定义

### 项目概述
[一段清晰的项目描述]

### 核心功能
1. 功能 1：描述
2. 功能 2：描述

### 技术要求
- 前端：xxx
- 后端：xxx
- 存储：xxx

### 验收标准
- [ ] 标准 1
- [ ] 标准 2

### 建议的实现步骤
1. 步骤 1
2. 步骤 2
3. ...
```

## 💡 最佳实践 (Best Practices)

### ✅ Do

* **主动推断**：基于常识补充用户未提及的合理需求
* **分层输出**：区分"必须有"和"最好有"的功能
* **提供选项**：给用户选择而非强加决定
* **保持简洁**：分析报告聚焦关键点，避免冗长

### ❌ Don't

* **过度假设**：不要凭空添加用户可能不需要的功能
* **技术偏见**：不要强推特定技术栈
* **忽略约束**：不要忽视用户提到的限制条件
* **过早细化**：初始分析不需要深入实现细节

## 📚 示例 (Examples)

### 示例 1：简短命令

**用户输入**：
> 写一个天气应用

**分析输出**：

```markdown
## 📊 任务分析报告

### 1️⃣ 用户需求
- **表面需求**：一个可以查看天气的应用
- **潜在需求**：可能需要多城市支持、天气预报、当前位置自动定位
- **隐含期望**：界面美观、响应快速、数据准确

### 2️⃣ 用户思路
- 可能期望简洁的单页应用
- 可能需要移动端适配

### 3️⃣ 背景上下文
- 项目类型：待确认（个人项目/学习项目？）
- 目标用户：普通用户

### 4️⃣ 约束与限制
- 需要天气 API（免费还是付费？）
- 是否需要后端？
- 是否需要用户账号系统？

### 5️⃣ 目标与验收
- **核心目标**：显示指定城市的天气信息
- **扩展目标**：多日预报、天气图标、背景随天气变化
- **交付物**：可运行的 Web 应用

---

## ❓ 建议确认

1. 是 Web 应用还是移动 App？
2. 需要支持多城市还是单城市？
3. 是否需要用户登录和保存偏好？
4. 对 UI 风格有什么偏好？

---

## 📋 优化后的任务定义

### 项目概述
创建一个天气查询 Web 应用，用户可以搜索城市查看实时天气和未来几天的预报。

### 核心功能
1. 城市搜索：支持城市名/拼音搜索
2. 实时天气：温度、体感温度、湿度、风力
3. 天气预报：未来 3-7 天预报
4. 自动定位：获取用户当前位置（可选）

### 技术建议
- 前端：React/Vue + TailwindCSS
- API：OpenWeatherMap / 和风天气
- 无需后端（纯前端调用天气 API）

### 验收标准
- [ ] 可以搜索城市并显示天气
- [ ] 天气数据准确且更新及时
- [ ] 界面美观、移动端适配
- [ ] 加载速度快（< 2s）
```
