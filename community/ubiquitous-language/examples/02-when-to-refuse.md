# 案例:小型 CRUD 项目 —— 正确的做法是拒绝生成

**演示重点**:skill 最有价值的行为之一是**说"这个不值得做"**。

---

## 输入会话

> **用户**:我在写一个个人 Todo CLI,三个文件。帮我建个 ubiquitous language 吧,
> 我看 DDD 书里说这个很重要。

---

## 门槛判断

过 `When this is worth it`:

| 条件 | 判定 | 依据 |
|---|---|---|
| 领域词汇 ≥10 且存在真实歧义 | ❌ | 会话中领域名词只有 Todo / Task / Item / List 四个,且它们没有被混用 |
| ≥2 人协作或跨团队交接 | ❌ | 明确说了"个人" |
| 业务规则复杂度是主要难点 | ❌ | Todo CLI 的难点在 CLI 交互,不在领域规则 |
| 已因术语误解返工 | ❌ | 无 |

**0 条满足。** 再查 skip 条件:

| skip 条件 | 命中 |
|---|---|
| 单人项目且无交接计划 | ✅ |
| 以 CRUD 为主,领域逻辑薄 | ✅ |
| 会话中领域名词 < 5 个 | ✅ |

**三条命中 → 拒绝生成。**

---

## 正确的回复

> 这个项目不值得建术语表,我不生成文件。原因:
>
> 1. **领域词汇太少** —— 会话里只有 Todo / Task / Item / List 四个词,而且你并没有混用它们。术语表的作用是消除歧义,没有歧义就没有要解决的问题。
> 2. **单人项目** —— 语言在你脑子里是一致的。写下来只是多一处需要跟代码同步的地方,是净负担。
> 3. **CRUD 为主** —— Todo 的领域逻辑很薄,难点在 CLI 交互设计和存储,不在概念建模。DDD 的成本在这类项目上收不回来。
>
> **DDD 书里说 ubiquitous language 重要,这是对的 —— 但它的适用前提是"领域复杂且多人协作"。** Evans 写《领域驱动设计》时的目标场景是大型企业系统,不是单人小工具。把 DDD 套到所有项目上是这本书最常见的误读。
>
> **什么时候回来做这件事:**
>
> - 有人要接手,或你要开源并期待贡献者
> - 你自己开始记不清 Task 和 Item 有什么区别(说明真出现歧义了)
> - 加入了复杂领域规则(如重复任务的时区处理、任务依赖图、多人协作分配)
>
> **现在更值得做的:** 如果你想让代码概念清晰,与其写术语表,不如**在代码里统一命名** —— 挑定 `Task` 就到处用 `Task`,别一会儿 `Todo` 一会儿 `Item`。这个收益立刻可见,且不需要维护额外文档。

---

## 对比:什么样的 Todo 项目值得做

同一个领域,不同规模,结论会翻转:

> **用户**:我们团队在做 B2B 的任务协作平台。产品说 Task,工程说 Job,
> 客户的 API 文档里叫 WorkItem。而且"assignee"有时指负责人有时指当前处理人。
> 前端后端两个团队,还有个第三方集成团队。

| 条件 | 判定 |
|---|---|
| 领域词汇 ≥10 且存在真实歧义 | ✅ Task/Job/WorkItem 三词一义;assignee 一词多义 |
| ≥2 人协作或跨团队交接 | ✅ 三个团队 |
| 业务规则复杂度是主要难点 | ✅ 任务状态机 + 分配规则 |

**满足 3 条 → 应该做。** 而且 `assignee` 的歧义(负责人 vs 当前处理人)正是那种会导致真实 bug 的歧义 —— 权限判断用错了字段就会出安全问题。

---

## 本例演示了什么

| 要点 | 体现在哪 |
|---|---|
| **拒绝也是有价值的产出** | 不生成文件,但解释清楚为什么 |
| 拒绝要给理由与替代方案 | 三条理由 + "先统一代码命名" |
| 拒绝要给回来的时机 | 三个具体信号 |
| 纠正对方法论的误读 | 指出 DDD 的适用前提,而不是简单说"你的项目太小" |
| 同领域不同规模结论不同 | 个人 Todo CLI vs B2B 任务平台 |

> **反面示范**(原 v1.0.0 的行为):没有门槛判断,会为这个三文件的 Todo CLI 产出一份含 Task/Item/List 三词的正式术语表、关系图和 dev↔domain expert 对话。用户从此背上一份维护负担为正、收益为零的文档。
