# 案例:软件工程师

## 用户画像

* **岗位**:独立开发者 / 小团队技术负责人
* **行业**:工具型 SaaS
* **工具现状**:VS Code + GitHub + Linear + Slack + Notion,跨 4 个工具追踪问题
* **核心痛点**:每天 30% 时间在"找上下文",状态变更散落各处

## 第一次访谈 (节选)

> **Q1**:岗位与角色?
> A:独立开发者 + 2 人小团队。
>
> **Q2**:30 天目标?
> A:(1) Issue 状态变更自动同步到 Slack (2) PR review 摘要自动生成 (3) 每周迭代复盘自动化。
>
> **Q3**:高频重复任务?
> A:读 issue 上下文、写 PR 描述、回复用户工单、迭代会议准备、复盘文档。
>
> **Q6**:本周最想跑通的一条?
> A:**PR review 摘要自动生成** — 每次 PR 都要手写 200 字描述。

## 诊断卡

```
你的系统定位:为小团队搭建"开发任务可追溯 + 沟通成本最小化"工作系统
当前成熟度:L3 (已有 Linear + Notion SOP,但未连通)
最大断点:跨工具状态不同步,每天重复解释背景
第一条闭环:PR 创建时 AI 自动生成 review 摘要
最小工具组合:Claude Code (主控) + GitHub Actions (触发) + Linear (任务)
本周先交付:GitHub Action 配置 + PR 模板
```

## 步骤压缩图

| 流程 | 现状人工步骤 | 目标人工步骤 | 步骤去向 | 验证指标 |
|---|---:|---:|---|---|
| 写 PR 描述 | 4 | 0 | 全自动 (Action 抓 diff → 生成描述) | 10min → 0 |
| Issue 状态同步 Slack | 3 | 0 | 全自动 (Webhook → Slack Bot) | 5min/次 → 0 |
| 每周迭代复盘 | 5 | 1 | 4 步自动 (汇总 issue → 总结 → 模板填充 → 推送) | 60min → 10min |

## 四层架构

```
统一入口:Claude Code (在 IDE 内直接调用) + Slack 命令
  ↓
AI 角色:
  - Claude Code 主控 (代码理解 + PR 摘要 + Issue 分析)
  - Slack Bot (状态播报 + 命令接收)
  ↓
业务系统:GitHub (代码) + Linear (任务) + Slack (沟通) + Notion (文档)
  ↓
资产沉淀:
  ├── 00_产品定位与迭代节奏.md
  ├── 01_架构决策记录 (ADR).md
  ├── 02_SOP_PR模板.md / SOP_Issue分类.md
  ├── 03_模板_PR_description.md / 模板_迭代复盘.md
  └── 04_执行记录_2026W34.md
```

## 第一个闭环详细设计

**触发方式**:GitHub Action `on: pull_request opened`

**输入**:
* PR 的 diff (`github.event.pull_request.diff`)
* 关联的 Issue 描述 (`pull_request.body` + Linear API)

**AI 执行**:
1. 解析 diff 识别:改动文件 / 关键函数 / API 变更
2. 读取关联 Issue 上下文
3. 生成 200-300 字 PR 描述:**目的 / 关键变更 / 测试覆盖 / 风险点**

**人工确认**:用户 review AI 生成的描述,补充业务背景

**外部动作**:自动评论到 PR,作为 reviewer 的快速入口

**输出**:PR 评论 + `04_执行记录.md`

**成功指标**:PR 描述撰写时间从 10min 降至 ≤1min,reviewer 阅读 PR 时间节省 ≥ 30%

## 合规检查

| 检查项 | 本案例的处理 |
|---|---|
| **数据分级** | 私有代码库 = **L2 机密**(泄露造成竞争损失) |
| **出境判定** | L2 走境外 AI 需前置条件:已确认使用企业版 + 已开启零数据留存 + 已获组织批准。**个人版不满足则不可用** |
| **凭证管理** | GitHub token / Linear API key 存 GitHub Secrets,不写入任何档案文件 |
| **对外动作** | PR 评论属仓库内部,非对外触达;不涉及个人信息 |
| **人审节点** | 架构变更类 PR 必须人工补充设计理由;AI 不得合并 PR |
| **自动化状态** | PR 描述生成 = 半自动(AI 生成草稿,人补业务背景后提交) |

> **若无法满足 L2 出境条件**:改用本地模型(如 Ollama + 代码模型)或只把 diff 的**文件名与函数签名**送给境外 AI,不送实现代码。

## 复盘 (6 周后)

* 73% PR 自动生成描述,27% 由用户补充业务背景(可接受)
* 关键学习:涉及"架构变更"的 PR,AI 描述常漏掉"为什么这样设计",需用户补充 — 这是**不可消除的人审环节**
* 关键学习:代码属 L2 机密,启用前先确认了企业版零留存设置 — 这一步容易被跳过
* 新增第二条闭环:每周迭代复盘自动化

## 不做的事

* ❌ 不让 AI 直接合并 PR(架构变更必须人工 review)
* ❌ 不让 AI 自动写 commit message(质量参差,价值有限)
* ❌ 不引入 Jira (Linear 已足够)
* ❌ **不在未确认零留存的情况下把私有代码送给境外 AI**
