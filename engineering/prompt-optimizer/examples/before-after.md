# Prompt优化前后对比示例

本文档展示真实的prompt优化案例，帮助理解优化技巧的实际应用。

---

## 案例1：代码审查请求

### ❌ 优化前

```
帮我看看这段代码有什么问题
```

### ✅ 优化后

```markdown
# 角色
你是一位资深的代码审查专家，专注于Python后端开发

# 任务
对以下代码进行全面审查

# 审查维度
1. **代码质量**：可读性、命名规范、代码结构
2. **性能问题**：时间复杂度、内存使用、潜在瓶颈
3. **安全漏洞**：SQL注入、XSS、敏感信息暴露
4. **最佳实践**：设计模式、SOLID原则、Python惯用法

# 代码
```python
[粘贴代码]
```

# 输出格式

按以下结构输出审查结果：

1. 总体评价（1-2句话）
2. 发现的问题（按严重程度排序）
3. 具体修改建议（附代码示例）
4. 优化后的完整代码

```

### 📈 改进点
- 添加了专家角色设定
- 明确了审查的具体维度
- 指定了结构化的输出格式
- 要求提供可操作的修改建议

## 案例2：会议纪要整理

### ❌ 优化前
```

整理一下这个会议记录

```

### ✅ 优化后
```markdown
# 任务
将会议录音转写稿整理为结构化的会议纪要

# 输入
[会议转写稿内容]

# 会议信息
- 会议名称：[名称]
- 参会人员：[人员列表]
- 会议日期：[日期]

# 输出要求
请按以下结构整理：

## 会议纪要模板
1. **会议概要**（50字以内）
2. **关键讨论点**（按话题分类）
3. **决议事项**（编号列表）
4. **行动项**（表格形式）
   | 事项 | 负责人 | 截止日期 |
   |------|--------|----------|
5. **遗留问题**（待下次讨论）

# 注意事项
- 过滤掉无关的寒暄内容
- 保留关键引用（使用引用格式）
- 对模糊决议标注"待确认"
```

### 📈 改进点

- 提供了会议的元数据
- 给出了清晰的输出模板
- 明确了表格格式的行动项
- 添加了处理规则（过滤、标注）

## 案例3：数据分析报告

### ❌ 优化前

```
分析一下这些数据
```

### ✅ 优化后

```markdown
# 角色
你是一位数据分析专家，擅长从数据中发现业务洞察

# 数据背景
- 数据来源：[来源描述]
- 时间范围：[时间区间]
- 业务场景：[场景说明]

# 数据集
[数据内容或描述]

# 分析目标
1. 识别主要趋势和模式
2. 发现异常值并解释原因
3. 提供可执行的业务建议

# 分析要求
- 使用统计指标支撑结论（均值、中位数、标准差等）
- 对比同期/环比数据
- 可视化建议（描述适合的图表类型）

# 输出格式
```markdown
## 数据概览
[数据基本统计信息]

## 核心发现
[3-5个关键发现，用数据支撑]

## 异常分析
[异常值识别及可能原因]

## 建议行动
[基于分析的可操作建议]

## 可视化方案
[推荐的图表类型及理由]
```

```

### 📈 改进点
- 提供了数据的业务背景
- 明确了分析目标和维度
- 要求用数据支撑结论
- 包含了可视化建议

## 案例4：产品需求文档

### ❌ 优化前
```

写一个登录功能的需求文档

```

### ✅ 优化后
```markdown
# 角色
你是一位经验丰富的产品经理

# 任务
撰写"用户登录功能"的产品需求文档(PRD)

# 产品背景
- 产品类型：[Web应用/移动App/...]
- 目标用户：[用户画像]
- 技术栈：[前端/后端技术]

# 文档结构要求
1. **功能概述**
   - 功能目标
   - 成功指标(KPIs)

2. **用户故事**
   - 格式：作为[角色]，我想要[功能]，以便[收益]

3. **功能需求**
   - 登录方式（账号密码/手机验证码/第三方OAuth）
   - 安全策略（登录失败限制、密码强度要求）
   - 记住登录状态

4. **交互设计**
   - 页面流程图（用Mermaid语法）
   - 状态说明（加载中/成功/失败）
   - 错误提示文案

5. **边界情况**
   - 网络异常处理
   - 账号状态异常（已禁用、未激活）
   - 多设备同时登录策略

6. **非功能需求**
   - 响应时间要求
   - 并发量预估
   - 日志记录需求

# 输出格式
Markdown格式，使用清晰的标题层级
```

### 📈 改进点

- 定义了完整的文档结构
- 包含用户故事格式
- 考虑了边界情况
- 添加了非功能需求

## 案例5：技术调研报告

### ❌ 优化前

```
调研一下React和Vue哪个好
```

### ✅ 优化后

```markdown
# 角色
你是一位中立的前端技术顾问

# 调研目标
为团队技术选型提供React和Vue的对比分析

# 项目背景
- 项目类型：[类型描述]
- 团队规模：[人数]
- 团队技术栈现状：[现有技术]
- 项目周期：[时长]
- 维护期望：[长期/短期]

# 对比维度
请从以下维度进行分析：

| 维度 | 说明 |
|------|------|
| 学习曲线 | 上手难度、文档质量 |
| 性能表现 | 渲染性能、包体积 |
| 生态系统 | 组件库、工具链成熟度 |
| 社区活跃度 | GitHub数据、StackOverflow |
| 企业采用 | 大厂使用案例 |
| 开发效率 | 开发体验、调试工具 |
| 长期维护 | 版本稳定性、迁移成本 |

# 输出格式
1. 各维度对比表格
2. 各维度详细分析
3. 基于我们项目特点的推荐
4. 推荐理由和潜在风险

# 要求
- 保持客观中立
- 数据要有来源
- 给出明确推荐（不要"各有优势"的结论）
```

### 📈 改进点

- 提供了项目背景（便于针对性建议）
- 明确了对比维度
- 要求给出明确推荐
- 强调客观性和数据支撑

## 总结：常见优化模式

| 模式 | 适用场景 | 示例 |
|------|----------|------|
| 角色设定 | 需要专业视角 | "你是一位资深..." |
| 结构化模板 | 复杂输出 | "按以下结构输出..." |
| 约束条件 | 避免发散 | "字数限制在..." |
| 示例驱动 | 格式要求高 | "参考以下示例..." |
| 反向约束 | 避免常见错误 | "不要出现..." |
| 评估标准 | 质量要求高 | "好的回答应该..." |
